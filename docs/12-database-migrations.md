# Database Migrations

## Goals

Lunchbench uses Cloudflare D1. Migration rules should be simple, explicit, and safe for production data.

The goals are:
- keep schema changes reviewable
- keep local and production schema behavior understandable
- avoid ad hoc production database edits
- keep seed data out of production unless explicitly intended

## Migration Location

SQL migration files live in:

```text
migrations/
```

Current files include:

- `0001_initial.sql`
- `0002_add_description.sql`
- `0003_add_vegan.sql`
- `0004_admin_sessions.sql`
- `0005_glicko.sql`
- `0006_glicko_defaults.sql`
- `0007_session_roles.sql`
- `0008_vegan_leaderboard_index.sql`
- `0009_matchup_sessions.sql`
- `0010_legacy_lunches.sql`
- `0011_sodabench.sql`
- `0012_soda_catalog.sql`
- `0013_soda_barcodes.sql`
- `0014_soda_barcodes_seed.sql`
- `0015_remove_olipop.sql`
- `seed.sql`

`0006_glicko_defaults.sql` repairs the schema defaults for new lunches, resets invalid-only self-match histories to the unrated Glicko baseline, drops copied self-match votes, and shifts obvious valid old-default `1000` starts onto the `1500` scale. It does not replay mixed historical Glicko games. Exact historical replay requires an explicitly approved repair command because the Glicko update is application logic, not SQL.

`0010_legacy_lunches.sql` adds `lunches.is_legacy` and sets it to `1` on every row present when it runs. Those are the Paula Legacy Lunch dishes from the previous caterer. Lunches created later default to `0`. `seed.sql` marks one sample lunch as legacy and four as non-legacy, because `GET /api/matchup` never serves legacy lunches. All sample lunches have a backdated `created_at` so they do not show the frontend "New" badge (lunches under 7 days old).

`0011_sodabench.sql` adds the Sodabench tables: `sodas` (catalog), `soda_swipes` (latest swipe per voter per drink), `soda_reports` (latest report per voter per drink), and `soda_buy_lists` (frozen weekly order snapshots keyed by `week_start`).

`0012_soda_catalog.sql` is data only. It inserts the original 124-drink catalog with `INSERT OR IGNORE` keyed by `walmart_item_id`, so re-running it adds nothing to a database that already has the catalog. On a fresh database it brings the 9 OLIPOP drinks back as active, so 0015 must follow it. It is generated by `node scripts/import-sodas.mjs sql` from `scripts/data/sodas.json`; do not edit it by hand. Its `image_key` values only resolve after the images are uploaded with `node scripts/import-sodas.mjs upload`. Production needs both steps, images first (see `docs/deployment.md`, all before merging). Local dev and E2E skip it and use the 14 sample drinks in `seed.sql` (same rows and keys). E2E uploads placeholder images for those keys from `scripts/data/seed-images`.

`0013_soda_barcodes.sql` adds `soda_barcodes` (13-digit GTIN `code` primary key, `soda_id`, `source` = `seed` | `voter` | `admin`, `created_at`) and `soda_unknown_scans` (one row per scan that matched no code: `code`, `format`, `session_key`, `created_at`, `resolved_soda_id`, `resolved_by` = `voter` | `admin`). Additive; the current Worker ignores both tables.

`0014_soda_barcodes_seed.sql` is data only. It maps Open Food Facts UPC/EAN codes to catalog drinks with `INSERT OR IGNORE`, joining `sodas` on `walmart_item_id`, and skips drinks that are not loaded. A re-run re-inserts the 19 OLIPOP mappings that 0015 deleted. Apply it after `0012_soda_catalog.sql` (production) or after `seed.sql` (local, E2E: maps the 14 sample drinks it covers). Any re-run of 0012 or 0014 must be followed by 0015. Otherwise the 9 OLIPOP drinks or their 19 seed barcode mappings come back, and those mappings block voter learning for the codes (`ON CONFLICT DO NOTHING`). It is generated by `node scripts/import-barcodes.mjs sql` from `scripts/data/soda-barcodes.json`; do not edit it by hand.

`0015_remove_olipop.sql` is data only and safe to re-run. It takes the 9 OLIPOP drinks off SodaArena (issue #296):
- it deletes their `soda_barcodes` rows, so a scanned OLIPOP can goes to manual search and is logged as unknown;
- it sets `is_active = 0` and `image_key = NULL` on their `sodas` rows.

Swipe and report history stays in place but is never shown, because every soda read path filters `is_active = 1`. Apply it after 0012 and 0014, including locally after loading the full catalog. Its R2 images are deleted separately (`docs/deployment.md`, "Remove OLIPOP").

0012 and 0014 have shipped, but `scripts/data/sodas.json` and `scripts/data/soda-barcodes.json` no longer list OLIPOP. So `import-sodas.mjs sql` and `import-barcodes.mjs sql` now refuse to overwrite their migration (`--force` overrides, for a deliberate, reviewed rebuild only). Catalog changes go in a new migration, like 0015. `worker/src/soda-catalog.test.ts` checks that each shipped migration, minus the drinks 0015 removes, still matches its JSON source.

Migration files should be append-only once merged. If a migration has shipped, create a new migration instead of editing history.

## Local D1

Use local D1 for development:

```bash
cd worker
npx wrangler d1 execute lunchbench --local --file=../migrations/0001_initial.sql
```

Apply later migrations in numeric order.

Seed local data only in local development:

```bash
cd worker
npx wrangler d1 execute lunchbench --local --file=../migrations/seed.sql
```

## Production D1

Production migrations must be deliberate.

Use:

```bash
cd worker
npx wrangler d1 execute lunchbench --remote --file=../migrations/<migration>.sql
```

Before applying production migrations:

1. Review the SQL.
2. Confirm it targets the intended D1 database.
3. Confirm whether the change is additive or destructive.
4. Confirm the deployed Worker code can handle the resulting schema.

Do not apply `seed.sql` to production unless the task explicitly requires production seed data.

## Compatibility Rules

Prefer additive migrations:

- add nullable columns first
- add tables before code depends on them
- backfill separately when needed
- add stricter constraints only after data is clean

Avoid combining destructive schema changes with unrelated feature work.

## PR Expectations

Schema PRs should include:

- migration SQL
- code that reads or writes the new schema
- tests or E2E coverage for the changed behavior
- docs updates if the schema affects API, deployment, or local setup

## Drift

If local, CI, or production schema appears to drift:

1. Stop changing data.
2. Document the observed mismatch.
3. Create or update an issue.
4. Fix through reviewed SQL migration or an explicitly approved repair command.

Do not hide schema repair inside an unrelated PR.
